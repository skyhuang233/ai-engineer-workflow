# Record Worker digests in release manifests

The exact GHCR digest cannot exist in the pull request that authorizes a Worker toolchain change because it is produced only after that commit enters `main`. The post-merge publisher therefore attaches a machine-readable `worker-release.json` to a source-keyed immutable GitHub Worker Release, binding the accepted source commit, Worker version, immutable image digest, pinned Codex and `no-mistakes` versions, upstream commit, fork release, release-asset checksum, deterministic Worker build-input identity, and Actions run. Release and image tags contain both the declared Worker version and the exact build-input identity, so any Worker source, Dockerfile, pinned publisher-workflow, or consumed toolchain-input change produces a distinct immutable release without a manual version bump. The build-input identity covers the `deploy/worker` Git tree, the pinned publisher-workflow blob, and the Worker toolchain inputs consumed by the build, using one base64-normalized canonical JSON serialization in both the publisher and Doctor. Git remains authoritative for build inputs, the Worker Release Manifest is authoritative for the cross-host build output, and SQLite records only which verified release is the current host's Active Worker Image. Doctor may accept a prior owner-accepted manifest only while its pinned inputs and build-input identity still equal those at current `main`; it also verifies that the identity matches the manifest's source commit. The manifest must be the sole asset for its exact source-keyed release, its digest must resolve, and its successful `push` run must belong to the active workflow at exactly `.github/workflows/publish-worker.yml`; its source commit must in turn have exactly one non-bot pull request merged by the configured owner. Missing, mismatched, or ambiguous provenance fails closed.
