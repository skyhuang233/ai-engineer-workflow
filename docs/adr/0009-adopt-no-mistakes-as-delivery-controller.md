# Adopt no-mistakes as the Delivery Controller

The Control Plane coordinates the issue dependency graph, Ticket Agents, Run Leases, containers, Ticket Workspaces, and incremental GitHub polling, while `no-mistakes` owns each ticket's rebase, automated review, tests, documentation checks, lint, and logical push, pull-request, and CI gates. In workflow mode the ephemeral Delivery Controller has no provider credentials: its push and pull-request steps issue lease-fenced Gateway commands, and its CI step explicitly delegates remote check, review, merge, and closed-unmerged observation to the long-lived Control Plane rather than fabricating a local success. The Control Plane may project checks-passed only from observed GitHub facts and retains human-only merge authority.

The Control Plane detects and deduplicates actionable pull-request feedback and routes it to the owning Ticket Agent. That feedback becomes the authoritative intent for a new Candidate Revision in the same Ticket Session; `no-mistakes` then reruns the complete delivery chain against the newly accepted immutable commit. The workflow integration forces every automatic fix limit to zero, so a finding can pause for a narrow human `approve` or `skip` decision but cannot mutate an already accepted Candidate. This preserves a narrow orchestration boundary and concentrates repository validation behavior in the open-source component already responsible for it.

Each ephemeral Delivery Controller container starts the supported `no-mistakes` daemon while mounting `NM_HOME` from the persistent Ticket Session state. The Worker image therefore includes the exact snapshot-pinned `procps` package needed by the daemon's detached-container fallback when systemd is absent. Candidate CI and production Doctor must both start the daemon and observe a successful status before the image can be accepted; a version-only binary probe is insufficient.

The first Delivery Controller launched in the Candidate handoff uses that Candidate Run's already selected Worker image. A later recovery retry is a new Worker Run and therefore uses the current Active Worker Image, while the accepted Candidate Revision retains its original runtime provenance unchanged. Every Delivery Controller Run records the actual image, tools, mounts, Gateway host mapping, and absence of GitHub write credentials in the Worker audit. This lets an accepted Candidate recover from a proven historical Worker defect without rewriting the Candidate, reusing a broken runtime, or bypassing validation.
